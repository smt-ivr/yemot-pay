# yemot-pay

Cloudflare Worker שמשרת את מערכות ימות המשיח של כמה לקוחות (multi-tenant) מעל מסד D1 אחד (`yemot-pay`).
כל המערכת הטלפונית בנויה בימות המשיח. ה-Worker אחראי רק על:

1. **בדיקת גישה לקורס** לפי הטלפון המתקשר, והצעה לרכוש אם אין גישה.
2. **הכנת הרכישה**: איסוף שני טלפונים לקורס (או טלפון ליצירת קשר לפגישה), אישור, ויצירת רכישה ממתינה.
3. **קליטת עדכון תשלום** מנדרים פלוס, הפעלת המנוי/ההזמנה ורישום ב-`payments`.
4. **תחזוקה יומית** (Cron): ביטול רכישות שלא שולמו, והעברת מנויים שלא חויבו ל-`failed`.

החיוב עצמו מתבצע בשלוחת הסליקה של נדרים פלוס בימות המשיח, לא אצלנו. אצלנו לא עובר מספר כרטיס.

## מבנה

```
src/
  index.ts            fetch + scheduled
  router.ts           ניתוב, זיהוי לקוח, אימות מפתח
  tenants.ts          רשימת הלקוחות המותרים: מזהה -> קידומת טבלאות
  db/                 שמות טבלאות מרשימה סגורה + שאילתות (הכל דרך bind)
  yemot/              פענוח בקשה מימות ובניית תשובות (read / id_list_message / go_to_folder)
  ivr/course.ts       שלוחת קורס: בדיקת גישה -> הצעה -> 2 טלפונים -> אישור -> מעבר לתשלום
  ivr/product.ts      שלוחת מוצר / פגישה / פגישה טלפונית
  payments/           מתאם לכל ספק (כרגע nedarim) + עיבוד עדכון התשלום
  billing/cron.ts     תחזוקה יומית
test/                 בדיקות מול D1 מקומי עם עותק של הסכמה
```

## Endpoints

| נתיב | מי קורא | תפקיד |
|---|---|---|
| `/ivr/:tenant/course` | שלוחת API בימות | בדיקת גישה לקורס / רכישה |
| `/ivr/:tenant/product` | שלוחת API בימות | רכישת מוצר / פגישה |
| `/pay/:tenant/nedarim?key=...` | נדרים פלוס (callback) | עדכון תוצאת חיוב |
| `/health` | – | בדיקת תקינות |

`:tenant` הוא המזהה מ-`tenants.ts`, למשל `zeevi-weiss`. מזהה שלא ברשימה מקבל 404.

## הגדרת שלוחת קורס בימות

```ini
type=api
api_link=https://<worker-domain>/ivr/zeevi-weiss/course
api_add_0=key=<המפתח של הלקוח>
api_add_1=course=c1          ; מזהה / ivr_code / שם הקורס
api_add_2=price=100          ; אופציונלי - ראו "מקור המחיר"
api_add_3=ok=/5/1            ; לאן להעביר מי שיש לו גישה (תוכן הקורס)
api_add_4=pay=/5/2           ; שלוחת הסליקה של נדרים פלוס לקורס הזה
api_add_5=exit=/             ; לאן לצאת (ברירת מחדל: ניתוק)
```

פרמטרים נוספים:
- `name`, `billing=monthly|one_time` – משמשים רק כשהקורס נוצר אוטומטית.
- `source=db|params` – מקור המחיר (ראו להלן).
- `mode=buy` – מדלג על בדיקת הגישה ועל תפריט ההצעה, ומתחיל ישר באיסוף הטלפונים. מתאים כשתפריט ההצעה בנוי בימות עצמה.

**מקור המחיר**
- `source=db`: המחיר נלקח מהגדרות הקורס בטבלה `courses`, וקורס שלא קיים מחזיר שגיאה.
- `source=params`: המחיר נלקח מ-`price` שבשלוחה. קורס שלא קיים נוצר אוטומטית עם `ivr_code` = `course`.
- בלי `source`: אם נשלח `price` משתמשים בו, אחרת במסד.

**שלוחת מוצר**: `product`, `price`, `name`, `type=product|meeting|phone_meeting`, `source`, `pay`, `exit`.

## זרימת תשלום

1. אחרי אישור הרכישה נוצרים מנוי `pending` עם הטלפונים (או הזמנה `pending`), והשיחה עוברת ל-`pay`.
2. נדרים פלוס שולחת עדכון ל-`/pay/zeevi-weiss/nedarim?key=...`.
3. העדכון משויך לרכישה לפי הסדר הבא:
   - הפניה מפורשת (`s123` / `o45`) אם הועברה;
   - מזהה הוראת קבע שנשמר ב-`subscriptions.card_token`;
   - טלפון המשלם + סכום: הרכישה הממתינה האחרונה של הלקוח.
4. מה קורה אחרי השיוך:
   - **חיוב ראשון מוצלח**: המנוי עובר ל-`active`, ו-`next_charge_date` נקבע לעוד חודש (קורס `one_time` מקבל `next_charge_date` ריק).
   - **חיוב חודשי מוצלח**: `next_charge_date` מתקדם בחודש.
   - **חיוב שנכשל**: `failed_attempts` עולה באחד. מנוי פעיל שמגיע ל-`maxFailedAttempts` עובר ל-`failed`. חיוב מוצלח מאוחר יותר מחזיר אותו ל-`active`.
5. עדכון כפול (אותו `transaction_id`) נרשם ולא מעובד שוב.

> ⚠️ **שמות השדות של נדרים פלוס לא אומתו.** המיפוי נמצא ב-`src/payments/nedarim.ts` (`NEDARIM_FIELDS`). כל עדכון נרשם ב-`ivr_log` עם הנתונים הגולמיים (ממוסכים), כך שאחרי עסקת ניסיון אפשר להשוות ולתקן רק שם.

## Cron

- רץ כל יום ב-06:00 UTC.
- מבטל רכישות `pending` שעברו `pendingTtlHours`.
- מעביר ל-`failed` מנוי חודשי שעבר את `next_charge_date` + `graceDays` בלי חיוב מוצלח.

## הוספת לקוח חדש

1. ליצור במסד את הטבלאות עם הקידומת החדשה (אותה סכמה).
2. להוסיף שורה ב-`src/tenants.ts`.
3. להוסיף מפתח ל-`TENANT_KEYS` ולעדכן את הסוד.
